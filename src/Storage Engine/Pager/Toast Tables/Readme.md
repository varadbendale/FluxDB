# Toast Tables

Let’s say you have some data which is really, really big. What can we do now? Since a page has a fixed size, the complete data may not be able to fit inside a single page. This is where Toast Tables come in. Pretty much, we take the large data, divide it into smaller parts, arrange those parts across a set of pages, and keep a record that these particular pages contain the different parts of the Toast Table. We can then use those pages together whenever we need to access the complete data.

We assign a number to each Toast Table chunk and put these chunks into a file which is specifically made to store the pages containing the Toast Table data. We then use another file as a map which specifically tracks all the pages, what number they have, where they are located, and all the other information required to access them. So whenever we need to retrieve the Toast Table, we can go through this map, get the file offset and slot number directly, and then use that information to access the required chunk.

The `get_toast_table_file_header` function contains all the header information which is needed for this. Going through the header, it basically tracks how many pages are being used, how many chunks have been used, and information about the chunks. The Toast Table's actual content, which is the huge data that we are trying to store, is divided into chunks, and each chunk is given a chunk ID. We also have the dead-space information, which tells us where reusable space is available inside the pages. Whenever we have enough available space, we can use that space to insert another Toast Table chunk and then continue moving forward.

The header also contains information about the map, such as which page offset the Toast Table chunk is located at and which chunk ID has been assigned to it. The `put_the_chunk_in_the_list` function handles this part. Whatever chunk we have inserted, we write its information into the map file and update the required information accordingly.

Coming to the insertion of Toast Tables, the first thing we do is find the size of the Toast Table that we need to insert. We then check whether there is any dead space available that can be reused. If there is, we first find which page contains the available space. There is also a limit on how much free space is worth keeping track of. If a certain amount of space is available, we mark it as dead space so that it can be reused. Otherwise, if the space is too small, we simply consider the page full because managing such a small amount of space is not worth it.

Once we find the page with available space, we check which slot is free and use that slot. The required information about the page, slot, offset, and the amount of data that can be stored is kept in the respective variables.

One important thing to mention here is that I have not rearranged the slot numbers every time we flush the whole thing. Since we have already written all the slot information into the file, whenever we need to insert data into the space of a dead chunk, we simply rearrange the slot offsets and move the data around. Whatever space we find at the end is then filled with the new data, and a new slot is used for it. The reason for doing this is that Toast Table chunks are already quite large, so the additional cost of rearranging the data and slots is acceptable.

The whole insertion process runs inside a loop. We continue moving through the loop until the complete Toast Table has been written. Each iteration handles as much of the remaining Toast Table data as possible, writes the required information, updates the map, and then continues with whatever data is still left.

Once we have found some available space, we check whether the page can accommodate the amount of Toast Table data that is still left. If the page can fit the whole remaining data, we simply put the entire thing into the page. We also keep some buffer space in consideration. The idea is that if only a small amount of data cannot be fitted, we should be able to accommodate that small amount without having to repeatedly search for another page.

After accommodating the data, we check how much space is left in the page. As mentioned earlier, only if the remaining space is greater than `612` bytes do we mark it as dead/free space. If the remaining space is less than or equal to `612` bytes, we simply consider the page full because maintaining such a small amount of free space is not worth the overhead.

If the page cannot accommodate the whole remaining Toast Table data, we reduce the amount of data that we are currently inserting to whatever can fit into the page. We write that portion into the page, update the map with the corresponding chunk information, and then continue the loop with the remaining Toast Table data.

The same thing happens when the page can accommodate the remaining data completely. In that case, we write the data into the page, check the remaining space, mark the space as dead if it is greater than `612` bytes, update the required information in the map, and then the Toast Table insertion is complete.

Now, if there is no dead space available at all, we need to create a new page. We first check the size of the remaining Toast Table data against the usable size of a new page. If the remaining data is larger than what the page can hold, we copy as much data as the page can accommodate, mark the page as used, write it to the file, put its information into the map, and then move forward with the loop to handle the remaining data.

If the remaining Toast Table data can completely fit inside the new page, we put the complete data into the page. We then check how much space remains after the insertion. If the remaining space is greater than `612` bytes, we declare that space as dead space so that it can be reused later. If it is less than or equal to `612` bytes, we simply declare the page full. Finally, we put the chunk information into the map and the Toast Table insertion is done.
